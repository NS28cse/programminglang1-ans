# 演習に添える実務の手引き（TA 用）

各回の演習に「実際のソフトウェア開発で必要になること」を 1 つずつ添えて教えるための，TA 用の実務の手引きである。授業時間は増やさない。
演習の巡回中に学生へ声をかけたり，1〜3 分だけ画面を見せたりするときに，そのまま使える文言と手順をまとめた。

## 使い方

- TA の仕事は，演習中に学生へ **1 対 1 で**教えることである。全員への説明はしない。
- 各回に**主テーマを 1 つ**，任意で**副テーマを 1 つ**割り当てている。巡回中にその場面
  （エラーで手が止まっている，境界の値を試していない，「動かない」と言っている など）に出会った学生に，1〜3 分で伝える。
- テーマごとの[説明用スライド](https://ns28cse.github.io/programminglang1-ans/)（`slides` ブランチ）がある。1 対 1 で説明するときに学生の画面で開いて要る 1〜2 枚だけを一緒に見るか，URL を伝えて後で読んでもらう（下の「[説明用スライド](#説明用スライド)」）。
- 演習の課題を終えることを優先する。ここに書いた内容を，課題の要求や採点の基準に加えない（担当教員の指示がある場合を除く）。
- 各回の節は「テーマと理由 → 声かけ → 見せ方 → 確かめる問い → よくある反応 → 副テーマ → デバッグの補足 → 関連」の順に並べた。「デバッグの補足」（一部の回だけ。任意）は，学生がバグで止まっている場面で 1 つだけ選んで使い，主テーマ・副テーマと同時には使わない。声かけと問いは，そのまま読み上げられる文にしてある。
- 文法・関数は，その回までに講義で扱ったものだけを前提にする。Visual Studio の操作のうち，その回までに授業で扱っていないもの（第2回の Git，第8回の Step Into・Watch 1・Call Stack など）は，各節に「（授業では未習。初めて見せる）」と書いた。
  授業資料での初出は，ブレークポイント・ステップオーバー・ローカル変数が第4回の講義，ウォッチが第13回の演習，ステップイン・呼び出し履歴が第14回の講義で，Git は授業資料に出てこない。
- 後半の「どの回でも使う型」（デバッグの進め方・テストケースの表・質問とバグ報告のテンプレート・レビューのチェックリスト・Git の手順・AddressSanitizer・AI 支援の扱い）は，各回の節から参照する。印刷して手元に置くと使いやすい。
- 各回の解答 README は解答を含むので，学生に画面を見せるときは学生自身のコード・演習ページ・この手引きの断片を使う。
- バグで止まった学生や，早く終えた学生にデバッガを練習させたいときは，[デバッグの題材](../debugging/README.md)（第4回〜第14回，誤りを 1 つ入れた短いプログラム）を渡す。各回の節の「関連」にその回の題材を挙げた。
- 各回の解答の一覧と `ta` ブランチの使い方（Visual Studio・VS Code の起動構成，テスト）は [TA.md](../TA.md)，ビルドの基本は[ルートの README](../README.md)にある。

## 第1回　エラーメッセージを読む（プログラミングの基礎）

**テーマと理由**: 課題3 `Broken` は，わざと `;` を抜いたコードの診断を読む課題である。実務でもビルドが失敗したら最初に診断を正確に読む。読まずにあちこち変えると原因が増える。
課題4 `Version`（保存とビルドは別）と合わせて，**1 件目を読む → 指された行とその前の行を見る → 直してビルドし直す** の順を身につけさせる。

**声かけ**
- 「エラーは上から 1 件目だけ読みましょう。ファイル名，行番号，説明の 3 つを言ってみてください」
- 「指された行に問題がなければ，1 つ前の行を見ます」
- 「ビルドに失敗したら，前回のビルドを実行するかの確認には **No** です」

**見せ方（2 分）**
1. `Broken` をビルドし，**View > Error List** を開く。**Code**（C2143）・**Description**・**File**・**Line**（6）の列を指す。
2. 項目をダブルクリックして 6 行目へ移り，「`return` の前に `;` がない」，つまり 5 行目の末尾が原因だと読む。
3. **View > Output**（**Show output from: Build**）にも `broken.c(6,5): error C2143` の形で同じ診断があることを見せる。
4. 直して **Build > Build Solution**，`1 succeeded` を確かめてから Ctrl+F5。

**確かめる問い**
- 問「診断は 6 行目なのに，直すのが 5 行目なのはなぜ？」→ C では改行は空白と同じなので，コンパイラは 6 行目の `return` を読んで初めて `;` がないと分かるから。
- 問「エラーが 10 件出たら，どれから直す？」→ 1 件目。1 か所の誤りが後ろの診断を連鎖させることがあるので，1 件直したらビルドし直す。

**よくある反応**
- 「6 行目を `;return 0;` にしたら通った」→ ビルドは通るが，直す場所の理解が違う。5 行目の末尾に付け直させる。
- 「`exe` は動いたので直った」→ 失敗したビルドの後に動くのは古い `exe`（課題4 と同じ）。**Output** の `succeeded` を確かめさせる。

**副テーマ（ビルドの成功と正しさは別）**: 課題2 `Message` で，演習ページの期待する表示と自分の出力を 1 行ずつ並べて比べさせる（空行・`"`・`\`・`%` の 1 文字の違い）。期待する出力と比べることが，テストのいちばん小さな形である（確認問題6）。

**関連**: 第1回 README の [課題3　エラーメッセージを読んで修正する](../week01/README.md#課題3エラーメッセージを読んで修正するbroken--brokenc)（MSVC・GCC・Clang の診断の比較，採点のポイント），[課題4　ソースファイルと実行ファイル](../week01/README.md#課題4ソースファイルと実行ファイルversion--versionc)，説明用スライド 「[エラーメッセージを読む](https://ns28cse.github.io/programminglang1-ans/error-messages/)」，「[再現できる質問](https://ns28cse.github.io/programminglang1-ans/bug-report/)」

## 第2回　バージョン管理を始める（変数）

**テーマと理由**: この回から「値を変えて試す → 元に戻す」が毎回の作業になる（課題1 `Rectangle` の `width = 6;` を 0・1 に，課題2 `Profile` の `%.2f` を `%f` に変えて最後に戻す）。
手で戻すと戻し忘れや戻し間違いが起きる。Git で **動いた状態を commit → 試す → 差分を見る → 戻す** を一度体験させる。詳しい手順は後述の「Git の最小の手順」。

**声かけ**
- 「期待する表示が出たら，値を変える前に commit しておきましょう。戻すのが 1 回の操作で済みます」
- 「どの行を変えたかは，**Git Changes** の差分で確かめてから戻しましょう」

**見せ方（課題を終えた学生に限る。2 回に分ける: 初めて声をかけたときは手順 0〜2 だけで 3 分，次に声をかけたときに手順 3〜4 で 2 分）**（授業では未習。初めて見せる）

0. **Git > Settings** の **Git Global Config** で **User name**・**Email** を確かめる（未設定なら入力）。
1. `Rectangle` のソリューションを開いたまま **Git > Create Git Repository** を選ぶ。**Create a Git repository** ダイアログの **Other** で **Local** を選び，**Initialize a local Git repository** の **Local path** を作業場所の `PL1` のフォルダにして **Create** を押す（Microsoft Learn の本文には **Create and Push** とあるが，**Local** を選んだ画面のボタンは **Create**。どこにもプッシュされない）。`PL1` 全体が 1 つのリポジトリになり，他の課題の `.sln` を開いても同じリポジトリが使われる。
2. `Rectangle` が期待する 3 行を出したら，**View > Git Changes** でメッセージ（例: `week02 Rectangle: 期待する表示`）を書いて **Commit All**。
3. `width = 6;` を `width = 0;` に変えて保存し，ビルド・実行する。**Git Changes** のファイルをダブルクリックすると，変えた 1 行が前（左）と今（右）で並ぶ。
4. ファイルを右クリックして **Undo Changes** → ソースが commit した状態に戻る。ビルドし直して元の 3 行が出ることを確かめる。

**確かめる問い**
- 問「commit は保存（Ctrl+S）と何が違う？」→ 保存はファイルを今の内容で上書きするだけ。commit はその時点の内容を履歴に残すので，後から比べたり戻したりできる。
- 問「**Undo Changes** の後，`Rectangle.exe` も元に戻っている？」→ 戻っていない。戻るのはソースだけなので，ビルドし直す（第1回 `Version` と同じ）。

**よくある反応**
- 「**Git Changes** に何も出ない」→ 保存していない，または開いたフォルダがリポジトリの外。`x64` や `.vs` が出ないのは `.gitignore` で除外しているためで正常。
- 「GitHub に上げないといけない？」→ 上げなくてよい。履歴は `PL1` の中の `.git` フォルダに入り，自分の PC の中だけで使える。課題の解答を公開の場所に置かない。

**副テーマ（警告を放置しない）**: **Error List** の **Warnings** ボタンを押して警告も表示させ，警告 0 で提出するよう伝える。MSVC の C4477（`printf` の書式と引数の型の不一致）は，表示がもっともらしく見えても誤りである（この組み合わせは演習ページの注意どおり実行して試さない）。
何も変えずにもう一度ビルドすると，ファイルが再コンパイルされないので警告が **Error List** から消えて見えることがある。警告が本当になくなったかは **Build > Rebuild Solution** で確かめる。
警告を見落とさない設定として，**C/C++ > General > Treat Warnings As Errors**（`/WX`）で警告をエラーとして扱う方法もある（授業の設定には含まれないので，手元で試す道具として紹介する）。

**デバッグの補足（デバッガの前に）**: デバッガは第4回から。この回は「実行する前に表示を予測して書く → 実行して比べる」が出発点になる。予測と違ったら，例えば `Rectangle` の再計算の前に `printf("width=%d area=%d\n", width, area);` を 1 行足し，どの代入の後から値が予測とずれたかを確かめる。確かめ終わったら足した行は消す（期待する表示と 1 文字も違えないため）。

## 第5回　読みやすいコードと関数の契約（配列と関数）

**テーマと理由**: 初めて自分で関数を作る回で，課題4 `Functions` は「計算は関数，表示は `main`」，発展 `SumMean` は「役割を分ける」課題である。コードは書く時間より読まれる時間の方が長い。
**名前で意味が分かる・1 つの関数は 1 つの仕事・数値には名前を付ける・受け付ける範囲（契約。呼び出す側との約束）をコメントに書く** の 4 点を確かめる。
「契約」は講義（6 節）・演習ページ（「関数の契約と検証」）と同じ用語である。
声をかけるのは，課題1 の `max_score` か課題4 の関数を書き終え，名前が `f`・`x`・`tmp` のままの学生と，「異なる配列で確かめる」の表で配列を変えたのに，呼び出しの `max_score(a, 5)` の 5 を表の配列に合わせて直し忘れている学生である。
1〜3 分で使うなら，まず声かけ 1 つと問い 3（`n = 0`）。課題を終えた学生には問い 4（どの配列で確かめるか）。

**声かけ**
- 「関数名と引数の名前だけで，何を受け取って何を返すか分かりますか」
- 「表の配列に変えたら，渡す `n` も表の『渡す `n`』の列に合わせましたか。配列より大きい `n` を渡すと配列の外を読むので，その実行結果は使えません」
- （次の手として）「同じ 5 が何か所にも出てきたら，`enum { COUNT = 5 };` のように名前を付けましょう。配列を宣言した `main` なら `sizeof a / sizeof a[0]` でも求められますが，`max_score` の中では使えません。受け取った `a` はポインタだからです」（演習ページ 課題1）

**見せ方（2 分）**: 次の 2 つの宣言は，同じ処理をする関数のものである（合格点 60 は第4回の講義の例）。どちらが読みやすいか，理由を 1 つ言わせる。

```c
int f(int a[], int n);   /* 本体は if (a[i] > 59) { ++r; } */

enum { PASS_SCORE = 60 };
/* 契約: n は 0 以上で，scores から n 個読めること。PASS_SCORE 以上の個数を返す */
int count_passed(const int scores[], int n);   /* 本体は if (scores[i] >= PASS_SCORE) { ++passed; } */
```

後者は，名前・`const`（配列を書き換えない）・契約のコメント・名前付きの定数で，本体を読まなくても使い方が分かる。
見せた後は，学生自身の `max_score` の宣言の前に契約のコメント（例:「契約: n は 1 以上で，a から n 個の要素を読めること」）があるかを確かめさせる。

**確かめる問い**
- 問「`average` の中で `printf` するのと，値を返して `main` で表示するのは何が違う？」→ 返せば呼び出し元で別の計算にも使える。表示しかしない関数は再利用できない（演習ページ「戻り値と表示を分ける」）。
- 問「`power` の受け付ける範囲（`base` は 1〜5，`exponent` は 0〜5）はどこに書く？」→ 関数の前のコメント。呼び出す側が守る条件（契約）なので，本体を読まなくても見える場所に書く。
- 問「`max_score` に `n = 0` を渡してよい？ `SumMean` の `sum_array` は？」→ `max_score` は最初に `a[0]` を読むので，契約は `n` が 1 以上（課題1 の「要素数 `n` は1以上」）。
  `sum_array` は 0 回のループで 0 を返すので `n` が 0 以上でよい。ただし `SumMean` の `main` は合計を `n` で割るので，`n` が 1 以上であることを呼び出す側で守る（契約は関数ごとに決まり，呼び出す側の前提とは別。演習ページ 発展）。
- 問「`max_score` が正しいことは，どの配列で確かめる？」→ 演習ページ「異なる配列で確かめる」の 4 行（要素が 1 個の {0}，全部同じ {60, 60, 60}，最初が最大，最後が最大）。`i < n - 1` で最後の要素を調べない誤りは，最後が最大の行（例 `{20, 30, 100}` で 30 になる）でだけ結果が変わる。表の行は「どの誤りなら結果が変わるか」で選ぶ（後述の「テストケースの書き方の型」）。

**よくある反応**
- 「短い名前の方が速く書ける」→ 読むのは 1 週間後の自分も含めて何度もある。ループの `i` のように慣例が決まっているものはそのままでよい。
- 「最初の表示 `average=3.0` が合ったので `average` は正しい」→ 戻り値の型を誤って `int` にしていても，`float result = average(2.0f, 4.0f);` の形なら (2 + 4) / 2 は割り切れるので表示には出ない（MSVC `/W4` では `float` から `int` への変換の C4244 が出る。GCC/Clang の `-Wall -Wextra` では出ない）。
  `printf("average=%.1f\n", average(2.0f, 4.0f));` のように直接渡す形なら，書式と型の不一致（MSVC は C4477，GCC/Clang は `-Wformat`）が出る。この形のまま実行しない（未定義動作。第2回と同じ）。まず戻り値の型を `float` に直して警告 0 にし，そのあとで `average(1.0f, 2.0f)` が 1.5 になるかを試させる。
  `float result = average(...);` の形なら実行してよく，`int` のままだと `average(1.0f, 2.0f)` が 1.0 になって誤りが表に出る。

**副テーマ（AI のコーディング支援を使う場合）**: 使ってよいかは授業の規則に従う。使う場合も，出てきたコードは自分で書いたコードと同じく境界の表（`power(2, 0)`・`power(5, 5)` など）で確かめ，説明できない行を残さない。
`^` を累乗の意味で使う（第3回のビット XOR）のように，もっともらしく見える誤りがあることを伝える。
- 場面: AI が出した `power` をそのまま貼って，`power=32` が出たところで終えている学生。
- 問「この `power` で `power(2, 0)` は何を返す？ 境界の表のどの行で確かめた？」→ 期待値は 1（base<sup>0</sup>）。AI の版が `result = base` から始める，`i <= exponent` にしている，などなら 2 や 4 が返り，表の `power(2, 0)` の行で見分けられる。答えられなければ，その行を実行させる。

**デバッグの補足（配列を渡したときの見え方）**: 学生の `main` の `max_score` を呼ぶ行と，`max_score` の `for` の行の両方に F9 でブレークポイントを置いて F5（関数の中で止めるのに F11 は使わない）。
先に `main` で止まり，**Locals** の配列は展開すると `{72, 85, 60, 93, 80}` の 5 要素が並ぶ。もう一度 F5（**Debug > Continue**。第4回で見せたもの）で `max_score` の中で止まり，**Locals** の `a` は `0x… {72}` のように先頭の 1 要素だけが表示される。
この違いは「配列を渡すと先頭の場所が渡る」（講義 4 節）の確かめになる。
任意の発展として（**Watch 1** と書式指定子は授業では未習），**Watch 1** に `a,5` のように「,要素数」を付けて書くと，`max_score` の中でも 5 要素を配列として表示できる。

## 第6回　容量と範囲外書き込み（文字列）

**テーマと理由**: 文字列のコピー・連結で容量を確かめずに書き込むと，配列の外を壊す。範囲外書き込みは実際のソフトウェアの代表的な脆弱性の 1 つで，C ではコンパイラも実行時も止めてくれないことがある。
課題4 `CompareJoin` の容量 10・9・8 と発展 `CopyCapacity` は，**書く前に「終端を含めて入るか」を確かめる** 練習そのものである。

**声かけ**
- 「書き込む前に，終端の 1 バイトまで入るか確かめましたか」
- 「容量ぴったり（9）と 1 つ足りない（8）を両方試しましょう」
- 「`strlen` と `sizeof` を並べて書くと，あと何バイト入るかが見えます」

**見せ方（2 分）**
1. `char text[10] = "hoge";` の 10 要素を紙に書かせ，「容量 10・長さ 4・終端の添字 4」を記入させる（演習ページの準備）。
2. 条件 `added < sizeof text - used` の `<` を `<=` にすると，容量 8 のとき 4 <= 4 が真になり `text[8]`（容量の外）へ書くことを，紙の上で確かめる（実行しない）。手元で確かめたい学生には，後述の「AddressSanitizer」を紹介する。
3. コピーのループ `i <= added` を `i < added` にすると終端を書かないが，この初期値（残りの要素が 0）では表示が変わらないことを口頭で伝え，「出力が合う」と「正しい」は別だと示す。

**確かめる問い**
- 問「容量 9 に `hogefuga` は入る？」→ 入る。8 文字＋終端 1 で 9 バイト，ぴったり。
- 問「容量の外に書いても，表示が正しく見えることがあるのはなぜ？」→ 範囲外の書き込みは未定義動作で，たまたま使っていない領域を壊すだけのこともあるから。表示だけでは安全かどうか分からない。

**よくある反応**
- 「`strcat` を使えば簡単」→ この課題は `strcat` を使わず，容量を確かめてからループで連結する（演習ページの課題4 の指示）。実務でも `strcat` は容量を確かめないので，使う場合は判定を自分で書いてから呼ぶ。
- 「MSVC では `strcmp(...) == -1` で動いた」→ `strcmp` の戻り値は符号だけが決まっていて，具体的な値は処理系で変わる。`< 0`・`== 0`・`> 0` で比べる。

**副テーマ（警告をキャストで黙らせない）**: `int i` と `size_t added` の比較で出る C4018（符号付きと符号なしの比較），`int used = strlen(text);` で出る C4267（`size_t` から `int` への変換。x64 構成で出て，Win32 構成では出ない）は，値の範囲を考え直す合図である。
`(int)` を付けて消すと警告だけが消えて誤りが残る。変数を `size_t` にそろえるのが正しい直し方（演習ページ「警告が出たらとにかくキャストする」直し方は避ける）。

**デバッグの補足（終端をメモリで見る。授業では未習）**: デバッグ中に **Debug > Windows > Memory > Memory 1** を開き，**Address** 欄に `text` と入れると，各バイトが 16 進で並ぶ。`hoge` なら 68・6F・67・65 の後に 00（終端 `'\0'`）が続く。連結の後に 00 がどこへ移ったかを見れば，`i <= added` の等号の意味が分かる（初期化で残りが 0 なので，`i < added` でも 00 が見えてしまうことも分かる）。**Memory** ウィンドウは **Tools > Options** の **Debugging > General** で **Enable address-level debugging** が有効なときに使える。
Debug 構成の実行時チェック（**Basic Runtime Checks**，`/RTC1`）は，**関数から戻るとき**に局所配列のすぐ外が書き換えられていないかを調べ，変数名を挙げてスタックの破壊を報告して止まる。止まるのは関数の終わりなので，その行ではなく，名前の出た配列への書き込み（特に容量の判定の差 1）を探す。すぐ外より遠くへの書き込みや，範囲外の読み取りは見つからない。

- 「指摘されるのは恥ずかしい」→ レビューは人ではなくコードを見るもの。TA も「ここはなぜ `<=` ？」のように質問の形で言う。

## 第12回　コンパイルとリンクを分けて考える（コンパイル）

**テーマと理由**: 実務のプログラムは多数のファイル（モジュール）に分かれ，ヘッダが「使い方の約束」，`.c` が実装になる。課題3 のエラーの比較は，ビルドの失敗を **前処理・コンパイル・リンク** のどこで起きたかで切り分ける練習である。
診断の番号の頭（`C` か `LNK` か）を見るだけで，直す場所の見当が付く。

**声かけ**
- 「エラー番号は C で始まりますか，LNK で始まりますか。LNK なら文法ではなく，ファイルの組み合わせの問題です」
- 「1 つ壊したら，記録して，元に戻して，成功を確かめてから次へ進みましょう」

**見せ方（2 分）**: 課題3 の 4 つの変更と，最初の診断を並べて見せる。

| 変更 | 段階 | 最初の診断（MSVC） | 直す場所 |
| --- | --- | --- | --- |
| `#include "calc_missing.h"` | 前処理 | C1083（インクルード ファイルを開けない） | ファイル名・保存場所・インクルードの検索先 |

**確かめる問い**

**よくある反応**

**副テーマ（ビルドの設定を文字で書く）**: Visual Studio のプロジェクト設定（どの `.c` を入れるか，**Additional Include Directories**，**Add > Reference**）は，実務では CMake などのビルドシステムで文字として書き，誰の PC でも同じようにビルドできるようにする。

## 第13回　所有者と失敗経路（メモリ管理）

**テーマと理由**: 解放後の使用・二重解放・解放忘れ（リーク）は，実際のソフトウェアの不具合や脆弱性の大きな原因で，正常な入力で 1 回動かしただけでは見つからない。課題4 は実行しないコードレビュー，
課題3 と発展3 は確保関数を「失敗したことにする」版に差し替えて**失敗経路をテストする**課題である。実務でも，起こしにくい失敗は差し替えで再現してテストする。

**声かけ**
- 「この `malloc` の領域の持ち主は誰ですか。どの `return` を通っても 1 回だけ解放されますか」
- 「失敗の模擬を 1 にして，`allocation failed` の後でメンバに触れていないか，ステップ実行で確かめましょう」

**見せ方（3 分）**
1. `NewPoint` のコピーを作り，演習ページの `point_allocate` を `new_point` の前に追加する。`new_point` の `malloc(sizeof *p)` を `point_allocate(sizeof *p)` に置き換え，`simulate_failure` を 1 にしてビルドする。
   - 正常版の `NewPoint` はそのまま残す。
   - このリポジトリでは，この手順 1 を済ませた版が `NewPointFail` である。TA が見せるときは，リポジトリの `NewPointFail` の本体は書き換えず，自分用のコピーで行う。
2. `Point *p = new_point(3.0, 4.0);` の行で F9，F5，F11 で `new_point` に入る（F11 は第8回で先取りしたもので，ステップ実行とウォッチはこの回の演習ページにも出てくる）。`point_allocate` が `NULL` を返し，`return NULL;` へ進んでメンバへの代入を通らないことを見せる。
3. `main` に戻ったら **Locals** で `p` が `0x0000000000000000` であることを確かめ，F10 で `fprintf` から `return 1;` へ進む（`p->x` を表示する `printf` は通らない）。
4. コピーの `simulate_failure` を 0 に戻すと正常出力になることを確かめる。正常版の `NewPoint` もビルド・実行する（演習ページのチェックリスト）。
   - このリポジトリでは，`const int simulate_failure = 1` を 0 に書き換えた版の期待する出力が [NewPointFail/variants/tests](../week13/NewPointFail/variants/tests/) の `simulate_failure_0.out` にある。書き換え方は [NewPointFail/CMakeLists.txt](../week13/NewPointFail/CMakeLists.txt) の `softprac_add_variant` に書いてある。

**確かめる問い**
- 問「`int *b = a; free(a); a = NULL;` の後，`b` も `NULL` になる？」→ ならない。`b` は古いアドレスのままで，`b[0]` を読めば解放後の使用，`free(b)` は二重解放。
- 問「メモリ不足の処理を確かめるのに，本当にメモリを使い切る必要がある？」→ ない。確保を担当する関数が `NULL` を返すようにすれば，失敗経路だけを安全に試せる。

**よくある反応**
- 「`p = NULL;` にしたから解放した」→ `NULL` の代入は解放ではない。`free(p);` の後に `p = NULL;`。`free` せずに `NULL` を代入するとリークになる。
- 「`int a[3]; free(a);` で後始末した」→ `free` に渡せるのは `malloc`・`calloc`・`realloc` が返したポインタか `NULL` だけ。自動変数の配列はブロックの終わりで寿命が終わる。

**副テーマ（レビューの手順）**: 演習ページのヒントの順（確保に成功した領域を数える → すべての `return` と失敗分岐で誰が解放するかをたどる → 別名のポインタと解放後の参照を探す）は，実務でメモリを扱うコードのレビューでもそのまま使える。
後述のチェックリストの「メモリ」の項目と合わせて使う。解放後の使用や範囲外アクセスを実行時に見つける道具として，後述の「AddressSanitizer」を紹介してもよい（授業では未習）。

**デバッグの補足（確保した領域をメモリで見る。授業では未習）**: Debug 構成の C ランタイムは，`malloc` した領域を 0xCD で埋め，その前後 4 バイトずつを 0xFD で埋めて確保する（Microsoft Learn「CRT debug heap details」）。`Dynamic` で `malloc` の直後に **Memory 1** に `values` と入れると，代入前の要素が CD の並びで，最後の要素の後ろに FD が 4 つ見える。**Watch 1** に `values,5` と書けば（コマンド引数を 5 にしたとき）5 要素を配列として見られる（「,要素数」の書式指定子は授業資料にない。第5回の「デバッグの補足」）。この FD を範囲外への書き込みで壊すと，`free` のときに Debug の C ランタイムが検査してエラーを報告する。アクセス違反で止まったときの見方は第8回と同じ。

## 第14回　推測せずに計測する（再帰）

**テーマと理由**: 発展1 `Fibonacci` は，素朴な再帰の呼び出し回数を数える課題である。`n = 20` で `fib` は 21891 回呼ばれるが，反復版 `fib_loop` はループを 20 回回るだけで済む。

**見せ方（2 分）**: 演習ページの表を埋めた後，再帰の呼び出し回数と反復の回数を並べる。

| `n` | `calls`（再帰版 `fib`） | ループの回数（`fib_loop`） |
| ---: | ---: | ---: |
| 5 | 15 | 5 |
| 10 | 177 | 10 |
| 20 | 21891 | 20 |

`calls` は `n` が 1 増えるごとに約 1.6 倍になる（同じ `fib(k)` を何度も計算し直すため）。ループの回数は `n` に比例するだけである。

**確かめる問い**
- 問「`fib(4)` は `calls` が 9，`depth` が 4。同時に待っている呼び出しは最大何個？」→ 4 個。左を計算し終えてから右を呼ぶので，同時に待っているのは根から今の呼び出しまでの 1 本の経路だけ。
- 問「再帰版の値が正しいと，どうやって確かめた？」→ 反復版の値と表のすべての `n` で比べた（2 つの実装の突き合わせ）。

**よくある反応**
- 「再帰は遅いから使わない方がいい」→ 一律ではない。遅いのは同じ計算を繰り返すから。木の走査（発展2）のように問題自体が再帰的なら，再帰の方が読みやすい。
- 「`n = 0` の `calls` は 0」→ 最初の呼び出しも数えるので 1（`depth` も 1）。`main` は数えない。

**副テーマ（自動テストと CI）**: 課題1 の「再帰版と反復版を 0〜20 のすべてで比べる」確認を，人が目で見る代わりにプログラムに任せるのが自動テストで，変更のたびに自動で実行する仕組みが CI（継続的インテグレーション）である。

## どの回でも使う型

### デバッグの進め方

1. **再現する**: 同じ入力・引数・操作で毎回同じ誤りが出る手順を書く（「質問・バグ報告のテンプレート」の再現手順）。出たり出なかったりするなら，未初期化の値や範囲外アクセスを疑う。
2. **範囲を絞る**: 「ここまでは正しい」と言える場所を探す。処理の中ほどで値を確かめ，正しければ後半，誤っていれば前半を調べる（二分して確かめる）。入力も，半分に削って再現するかを試す。
3. **仮説を立てる**: 「`sum = 0;` がループの中にあるので最後の値しか残らない」のように，原因と，それが正しければ何が見えるはずかを 1 文で言う。
4. **確かめる**: デバッガ（ブレークポイント・ステップ・ウォッチ・メモリ）か `printf` で，予想した値と実際の値を比べる。外れたら 2 に戻る。
5. **直す**: 1 か所だけ直し，再現手順でもう一度確かめる。
6. **テストを足す**: 同じ誤りを捕まえる入力と期待する出力を，テストケースの表に足す（境界の値であることが多い）。

`printf` とデバッガの使い分け:
- デバッガ: 止めて多くの変数をまとめて見たい，どの経路を通ったかを 1 文ずつ追いたい，ポインタの指す先やメモリを見たいとき。ソースを変えないので，消し忘れが起きない。
- `printf`: 長いループの値の変化を 1 画面で見たい，止めると様子が変わるとき。調べるための出力は `fprintf(stderr, ...)` で `stderr` に出し（第7回以降），期待する表示（`stdout`）に混ぜない。確かめ終わったら消してから提出する（Git の差分で消し忘れを確かめられる）。

### テストケースの書き方の型

演習の「予測 → 実行結果 → 理由」の記録は，そのままテストケースの表になる。実行する**前に**「期待する出力」まで埋め，実行後に「実際の出力」と「一致」を埋める。

| # | 入力（変えた値） | 種類 | 期待する出力 | 実際の出力 | 一致 | 理由 |
| ---: | --- | --- | --- | --- | --- | --- |
| 1 | `age = 10` | 通常 | `500` | | | 6〜17 歳は 500 |
| 2 | `age = 5` | 境界（無料の最後） | `0` | | | 0〜5 歳は 0 |
| 3 | `age = 6` | 境界（500 の最初） | `500` | | | |
| 4 | `age = 17` | 境界（500 の最後） | `500` | | | |
| 5 | `age = -1` | 異常 | `invalid` | | | 負の年齢は不正 |

（第4回 `Fee` の例。）値は次の観点で選ぶ。

- 境界: ちょうど・1 つ手前・1 つ先（第3回，第4回 `Fee`）
- 繰り返し: 本体が 0 回・1 回・複数回・許される最大（第4回 `EvenSum`）
- 文字列・配列: 空・1 要素・容量ちょうど・容量を 1 超える（第6回 `CompareJoin`，第7回 `LineInput`）
- 異常: 形式が違う（`12x`）・範囲外・不足・過剰（第10回）
- 誤りを見分ける値: 誤った書き方と正しい書き方で結果が分かれる値（第3回 `Leap` の 1900）

### 質問・バグ報告のテンプレート

```text
【何をしたか（再現手順）】 ByteCount を Ctrl+F5 で起動し，abcd と入力して Enter を押した
【期待した結果】           5 と表示される
【実際の結果】             何も表示されず，入力待ちのまま
【試したこと】             ビルドし直した（成功）。Enter を何回押しても同じ
【コード】                 問題が起きる最小のコード，またはその関数だけ
【環境】                   Visual Studio 2026，Debug，x64
```

- 再現手順には，押したキー（Enter，行頭の Ctrl+Z）・コマンド引数・入力ファイルの内容まで書く。
- 実際の結果は，出力やエラーメッセージを言い換えずにそのまま貼る。エラーなら 1 件目の番号と行番号を書く。
- 最小の再現コード: 問題が起きる部分だけを残して削る。例えば第8回の「交換されない」は次のコードで再現できる。
  `a = b;` はポインタのコピーを入れ替えるだけで `x` の箱に書き込まない，という原因は，ここまで削ると見えやすい。

```c
#include <stdio.h>

void swap(int *a, int *b)
{
    int *temp = a;
    a = b;
    b = temp;
}

int main(void)
{
    int x = 3;
    int y = 8;
    swap(&x, &y);
    printf("x=%d y=%d\n", x, y);   /* 期待: x=8 y=3，実際: x=3 y=8 */
    return 0;
}
```

### コードレビューの観点チェックリスト

読む前に「何をする関数か（契約）」を作者に 1 文で言ってもらい，それと比べながら読む。指摘は「なぜ〜？」の質問の形にする。

- [ ] 仕様: 受け付ける範囲（契約）がコメントにあり，境界の扱い（`<` か `<=` か）が仕様と一致している（第5回，第11回 `RectContains`）
- [ ] 名前: 変数・関数の名前で役割が分かる。同じ数値が何度も出てこない（第5回）
- [ ] 初期化: 読む前に値が入っている。累積の変数はループの前で初期化している（第4回 `EvenSum`，第11回 `normalized`）
- [ ] 範囲: 添字は 0〜`n - 1`。書き込む前に終端を含めて容量を確かめている（第5回，第6回，第8回 `CopyText`）
- [ ] 戻り値: `fgets`・`fopen`・`strtol`・`malloc` などの失敗を調べている。関数は失敗を戻り値で返し（出力先は変更しない），`main` が `stderr` へ出して `return 1;` で終わる（第8回 `CopyText`，第10回，第12回 `calc_divide`，第13回）
- [ ] 型と警告: 警告 0。キャストで警告を消していない（第2回，第6回，第9回）
- [ ] コピーと共有: 構造体やポインタのコピーで，中身が複製されるのか共有されるのかを区別している（第9回，第11回）
- [ ] メモリ: 確保した領域の所有者が 1 つに決まり，すべての `return` で 1 回だけ解放する。解放後に使わない（第13回）
- [ ] 再帰: 基底条件と，呼ぶたびに小さくなる量がある。入力は再帰に入る前に検査している（第14回）

### Git の最小の手順（Visual Studio の Git Changes）

学生が自分の課題フォルダの履歴を，自分の PC の中に残すための手順である。GitHub などへ公開する必要はない。課題の解答を公開の場所に置かないこと。

**最初に 1 回**
1. **Git > Settings** を開き，**Git Global Config** の **User name** と **Email** を確かめる（未設定なら入力。commit に記録される名前で，公開しないので自分が分かる値でよい）。
2. 課題のソリューションを開いたまま **Git > Create Git Repository** を選ぶ。**Create a Git repository** ダイアログの **Other** で **Local** を選び，**Initialize a local Git repository** の **Local path** を作業場所の `PL1` のフォルダにして **Create** を押す（**Local** ならどこにもプッシュされない）。
   **.gitignore template** を Visual Studio 用のままにすると，`x64` や `.vs` などのビルドの生成物は履歴に入らない。
   （VS 2022 ではこの選択肢が **Local only**。ボタンは同じ **Create**。）
3. 以後は各課題の `.sln` を開けば，`PL1` のリポジトリが使われる。

**毎回の作業**

| したいこと | 操作 |
| --- | --- |
| 変更したファイルの一覧を見る | **View > Git Changes** |
| 差分を見る | **Git Changes** のファイルをダブルクリック（左が前回の commit，右が今のファイル） |
| commit する | メッセージ（例: `week03 Leap: 1900 を含む 4 年で確認`）を書いて **Commit All** |
| 保存した変更を前回の commit の状態に戻す | ファイルを右クリック → **Undo Changes**（commit していない変更は消える） |
| 履歴を見る | **Git > View Branch History** |
| commit した後で実験を取り消したいとき | 履歴で commit を右クリック → **Revert**（取り消す変更を新しい commit として記録する） |

- commit は「1 つの意味のある変更」ごと。動いたら commit，実験の前に commit。
- 戻したらビルドし直す（ソースが戻っても `exe` は戻らない）。
- VS Code では **Source Control** ビュー（Ctrl+Shift+G）で同じことができる。コマンドでは，最初に `git init`，commit は `git add -A` と `git commit -m "メッセージ"`，差分は `git diff`，戻すのは `git restore <ファイル>`。

### AddressSanitizer（範囲外アクセスと解放後の使用を実行時に見つける）

授業の課題では使わなくてよい。手元で確かめる道具として，第6回・第13回で興味を持った学生に紹介する（授業では未習）。
プロジェクトの **Configuration Properties > C/C++ > General > Enable AddressSanitizer** を **Yes (/fsanitize=address)** にして F5 で実行すると，配列の外への書き込みや解放後の使用が起きた所で止まり，その種類が表示される。Ctrl+F5 で実行した場合は，報告がコンソールに表示される。
AddressSanitizer は Edit and Continue（`/ZI`）・`/RTC`（実行時チェック）・インクリメンタル リンク（`/INCREMENTAL`）と併用できない（Microsoft Learn の「AddressSanitizer」）。Debug 構成では次の 3 つを変える。

- **C/C++ > General > Debug Information Format** を **Program Database (/Zi)**
- **C/C++ > Code Generation > Basic Runtime Checks** を **Default**
- **Linker > General > Enable Incremental Linking** を **No (/INCREMENTAL:NO)**

設定はプロパティ ページ上部の **Configuration** が **Debug** であることを確かめてから変え，試した後は 4 つとも元に戻す（または試す用のプロジェクトのコピーで行う）。提出する課題は授業の設定のままにする。
見つかるのは実行した経路の誤りだけなので，境界の値のテストと組み合わせて使う。

### AI のコーディング支援を使う場合

- 使ってよいか，どこまで使ってよいかは授業の規則（担当教員の指示）に従う。
